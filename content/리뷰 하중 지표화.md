# 리뷰 하중 지표화

## 한 줄 정의
AI 코딩 에이전트 도입으로 급증한 코드 리뷰 요청을 정량화하고 모니터링하여, 특정 시니어 개발자에게 편중되는 인지적 부하(Review Load)를 분산하고 제어하는 관리 워크플로우이다.

## 핵심 요지
- **인지적 비용의 정량화**: 단순 PR 개수가 아닌, 코드 변경 줄 수(LOC) 및 파일 영향도, 비즈니스 영향도를 고려하여 리뷰 하중을 측정한다.
- **의무적 부하 분산(Load Distribution)**: 특정 시니어에게 리뷰 요구가 쏠리는 현상을 감지하고, 리뷰어 지정을 의무적으로 다각화한다.
- **엄격한 PR 상한제(Cap/Throttle)**: 꼼꼼한 검토가 가능하도록 개별 PR 크기와 단위 시간당 생성 가능한 에이전트 PR의 총 개수를 조정한다.
- **창작 시간 보장(Creative Time Allocation)**: 시니어가 하루 중 일부 시간을 주도적인 설계(Building) 및 아키텍처 수립에 사용하도록 업무를 의도적으로 재할당한다.
- **정성적 정기 피드백 연동**: 일대일 미팅을 통해 수치상 드러나지 않는 심리적 무력감과 번아웃을 선제적으로 예방한다.

## 상세
### 1. 리뷰 하중 지표화의 필요성
AI 코딩 에이전트를 도입하면 개발 속도(Velocity)나 PR 병합 주기, 처리량(Throughput) 등의 표면적 지표는 급격히 개선되지만 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`), 이는 하류(Downstream)에 위치한 [[검증 레이어]]의 침묵하는 희생 위에 서 있을 확률이 높다. AI가 작성한 세련되어 보이지만 교묘한 에러를 포함한 대량의 코드는 결국 시니어 엔지니어의 책상 위로 집중되어 [[코드 리뷰 대기열 병목]]을 유발한다.

실제로 AI 도입 후 코드 리뷰 소요 시간은 약 200% 증가했고, 엔지니어링 리더의 86%가 시니어 엔지니어가 버그 수정에 더 많은 시간을 쓰고 있다고 대답했다 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`). 이러한 비정상적인 인지적 하중을 방치하면 결제 파이프라인과 같은 핵심 아키텍처의 도메인 지식을 가진 유일한 시니어 인재가 퇴사하게 되며, 이로 인한 직간접 비용은 15만 달러에서 30만 달러에 달한다 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`). 따라서 배포 주기만큼이나 '리뷰 하중(Review Load)'을 체계적으로 지표화하고 모니터링하여 방어선을 구축해야 한다.

### 2. 리뷰 하중 지표화 워크플로우 5단계

#### 1단계: 리뷰 하중 점수(Review Load Score) 정의
단순히 처리된 PR의 개수만 측정하면 인지적 노력을 제대로 반영하지 못한다. 리뷰에 들어가는 '인지적 비용(Cognitive Expense)'을 수식화하여 지표화해야 한다.
- **리뷰 하중 산출 모델 예시**:
  $$\text{Review Load Score (RLS)} = \sum_{i=1}^{n} \left( \text{LOC}_i \times \text{Complexity Weight}_i \times \text{Reviewer Cognitive Cost}_i \right)$$
  - $\text{LOC}_i$: 해당 PR의 총 변경 코드 라인 수 (Lines of Code)
  - $\text{Complexity Weight}_i$: 변경 파일 개수 및 아키텍처 중요도 가중치 (예: 결제 도메인은 2.0, 단순 UI는 1.0)
  - $\text{Reviewer Cognitive Cost}_i$: 리뷰를 수행하는 인원의 숙련도에 따른 인지 피로 가중치 (시니어는 1.2, 주니어는 0.8)

#### 2단계: RLS 분산 모니터링 및 실시간 시각화
매니저는 대시보드를 통해 팀 전체의 생산성 곡선뿐만 아니라, **엔지니어 개인별 RLS의 누적 곡선**을 모니터링해야 한다. 특정인에게 RLS가 과도하게 집중되는 현상이 발견되면 즉시 경보(Alert)를 울린다.

#### 3단계: PR 크기 및 개수의 엄격한 상한선(Cap & Throttle) 설정
- 지쳐 쓰러진 시니어가 시간에 쫓겨 11분 만에 훑어보고 넘긴 에이전트의 400줄짜리 PR은 잠재적 장애에 면죄부를 발행하는 위험을 내포한다 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`).
- 1회 제출 PR의 변경 크기는 최대 200 LOC로 조율하고, 단위 시간당 리뷰 큐에 쌓일 수 있는 에이전트의 PR 총 개수에 캡(Cap)을 씌워 시니어가 각 PR을 깊이 있게 검증할 최소 시간(최소 30분 이상)을 확보한다.

#### 4단계: 시니어 개발자 창작(Building) 시간 의도적 재할당
- 시니어 개발자가 하루 종일 에이전트 코드의 뒷수습하고 숨은그림찾기 식 버그 수정에만 머무른다면 극심한 무력감을 겪으며 퇴사하게 된다 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`).
- 아키텍처 설계, 신규 모듈 기획, 비즈니스 핵심 로직의 직접 구현 등 지적 만족감과 성취감을 느낄 수 있는 창의적인 '창작(Building)' 활동을 일과 시간의 최소 30%~50% 이상 의도적으로 배정해야 한다.

#### 5단계: 정성적 피드백 수집 및 선제적 모니터링
- 일대일 미팅에서 다음과 같은 정성적 질문을 집요하게 던져 사직서를 받기 전에 번아웃의 징후를 조기에 탐지한다 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`):
  > "지금 맡고 있는 역할이 여전히 가치 있게 느껴지나요? 이 일이 정말 하고 싶었던 일인가요?"
- 부정적 기류가 감지되는 즉시, 리뷰 하중 분산 정책을 가동하여 안전한 업무 환경을 복원한다.

## 예시
### 1. 리뷰 하중(Review Load) 계산 및 경고 자동화 스크립트 (Python)
다음은 GitHub API로부터 PR 정보를 추출하여 담당 리뷰어의 인지적 리뷰 하중 점수(Review Load Score)를 계산하고, 일일 제한치(Threshold)를 넘는 경우 슬랙 등으로 경고를 발생시키는 자동화 파이프라인의 핵심 코드 예시이다.

```python
import os
import requests

GITHUB_API_URL = "https://api.github.com"
GITHUB_TOKEN = os.getenv("GITHUB_TOKEN")
SLACK_WEBHOOK_URL = os.getenv("SLACK_WEBHOOK_URL")

# 설정값
COGNITIVE_LIMIT = 500  # 일일 권장 리뷰 하중 한계치
HEADERS = {"Authorization": f"token {GITHUB_TOKEN}", "Accept": "application/vnd.github.v3+json"}

def calculate_pr_load(pr_data):
    """PR 변경 라인수, 파일 수, 도메인 영향도 기반 리뷰 하중 계산"""
    additions = pr_data.get("additions", 0)
    deletions = pr_data.get("deletions", 0)
    changed_files = pr_data.get("changed_files", 0)
    
    # 멱등성 및 결제 등 핵심 아키텍처 파일 포함 여부 체크 (가중치 부여)
    is_core_path = any(
        "payment" in f["filename"] or "checkout" in f["filename"]
        for f in pr_data.get("files", [])
    )
    domain_weight = 2.0 if is_core_path else 1.0
    
    # RLS 공식: (추가 라인수 + 삭제 라인수 * 0.5) * 파일 개수 가중치 * 도메인 가중치
    load_score = (additions + deletions * 0.5) * (1 + changed_files * 0.1) * domain_weight
    return int(load_score)

def audit_reviewer_load(owner, repo, username):
    """특정 리뷰어의 할당된 활성 PR 리뷰 하중 감사"""
    # 1. 리뷰 대기 중인(requested) open PR 조회
    query_url = f"{GITHUB_API_URL}/repos/{owner}/{repo}/pulls?state=open"
    response = requests.get(query_url, headers=HEADERS)
    prs = response.json()
    
    total_load = 0
    assigned_prs = []
    
    for pr in prs:
        # 리뷰어 지정 확인
        reviewers = [r["login"] for r in pr.get("requested_reviewers", [])]
        if username in reviewers:
            # 개별 PR 상세 정보 (additions, deletions, changed_files 조회)
            pr_detail_url = pr["url"]
            pr_detail = requests.get(pr_detail_url, headers=HEADERS).json()
            # 파일 리스트 조회 추가
            files_url = f"{pr_detail_url}/files"
            pr_detail["files"] = requests.get(files_url, headers=HEADERS).json()
            
            pr_load = calculate_pr_load(pr_detail)
            total_load += pr_load
            assigned_prs.append({"number": pr["number"], "load": pr_load})
            
    # 2. 임계값 초과 시 경보 송신
    if total_load > COGNITIVE_LIMIT:
        alert_msg = (
            f"⚠️ *리뷰 하중 경보* ⚠️\n"
            f"엔지니어 *{username}* 님의 현재 리뷰 하중({total_load} RLS)이 일일 인지 임계치({COGNITIVE_LIMIT})를 초과했습니다.\n"
            f"대기열 조율 및 PR 분산이 권장됩니다.\n"
            f"상세 PR 목록: {assigned_prs}"
        )
        requests.post(SLACK_WEBHOOK_URL, json={"text": alert_msg})
        print(f"Alert Sent for {username}: {total_load} RLS")
    else:
        print(f"Reviewer {username} is within safe load limits ({total_load} RLS).")

# 실행 예시 (A사 결제 모듈 저장소 감사)
if __name__ == "__main__":
    audit_reviewer_load("my-org", "payment-service", "priya-dev")
```

### 2. 가상의 개선 시나리오
- **도입 전**: AI 에이전트 도입 직후 PR 건수가 주당 15건에서 60건으로 폭증했다. 결제 모듈의 모든 검증 책임은 시니어인 프리야에게 집중되었다. 프리야의 일일 리뷰 하중은 일 평균 1,200 RLS에 달해, 매주 120%의 야근 속에서도 병목은 더욱 곪아갔으며 결국 극심한 무력감으로 사직서를 내밀기 직전까지 몰렸다.
- **도입 후**: 매니저가 '리뷰 하중 지표화'를 수립하여 RLS 시스템을 도입했다. 일일 RLS 상한선을 400으로 두고, 프리야에게 배정되던 단순 UI 및 비핵심 API PR은 주니어 엔지니어들과 다른 팀 시니어들에게 분산시켰다. 멱등성 및 결제 경로의 핵심 PR에만 프리야를 할당하고, 프리야에게는 신규 대용량 결제 캐싱 아키텍처 설계 시간을 전체 일과의 40%로 보장해 주었다. 그 결과 전체 배포 속도는 15% 정도 다소 조정되었으나, 시스템 장애율은 오히려 40% 감소했으며, 프리야의 무력감도 해소되어 팀의 기술 리더십이 안전하게 유지되었다.

## 충돌
### AI에 의한 리뷰 자동화와 지표 관리의 대립
- **일부 아키텍트들의 주장**: 리뷰 하중을 줄이기 위해 '리뷰 하중 지표화'와 같은 인간 관리 프로세스를 수립할 필요 없이, AI 에이전트 간의 상호 크로스 리뷰(AI Cross-Review) 파이프라인을 구축해 인간 검증 단계를 생략하자는 기술 중심의 해결책을 제시한다.
- **소스 문서의 상충 결과**: 그러나 실제 운영 환경에서 AI 상호 리뷰를 도입한 시도는 빌드 테스트(`green`)와 피상적 로직 검증만 성공했을 뿐, 비즈니스 논리적 맹점을 걸러내지 못하여 프로덕션 시스템이 전면 먹통이 되는 치명적인 배포 사고 위기를 초래했다 (`raw/My Best Senior Engineer Quit Last Month. Her Exit Interview Was Scheduled for Forty Minutes. The Last Five Changed How I Run My Team..md`).
- **결론**: 따라서 AI 상호 리뷰는 리뷰 하중의 정량적 점수를 약간 경감해 주는 보조 도구로만 제한되어야 하며, 인간 시니어의 복합 직관에 근거한 검증 레이어 자체를 생략하거나 이를 지표화하여 보호하는 워크플로우를 대체할 수 없다.

## 관련 노트
- [[코드 리뷰 대기열 병목]]: AI 에이전트의 대량 생산으로 인한 리뷰 큐 적체 현상의 메커니즘을 상세히 다룬다.
- [[검증 레이어]]: 인간 시니어 엔지니어가 에이전트의 결과물을 필터링하는 최종 수비수로서 마주하는 번아웃 문제를 설명한다.
- [[제본스의 역설 (Jevons Paradox)]]: AI 도입으로 코딩 단가는 극적으로 낮아졌으나, 아이러니하게도 최종 검증을 위한 시니어의 인지 하중과 비용이 폭발적으로 급증하는 경제학적/조직적 현상을 연계하여 고찰할 수 있다.
- [[AI 코딩 에이전트 검증 전략]]: 에이전트의 오작동 리스크를 통제하고 시스템의 회복 탄력성을 지탱하기 위한 구체적인 수동/자동 검증 프로세스를 다룬다.
