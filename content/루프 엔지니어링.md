# 루프 엔지니어링 (Loop Engineering)

## 한 줄 정의
단발성 프롬프트 입력을 넘어, 에이전트가 스스로 프롬프트를 생성하고 목표를 달성할 때까지 자율적으로 수정·검증·평가 사이클을 무한히 반복하도록 설계하는 자율 시스템 제어 기술.

## 핵심 요지
- **개발자 병목 제거**: 테스트 결과 확인, 에러 리포트 분석, 재차 수정 프롬프트 입력 등 사람이 개입해 상황을 대조하던 반복적인 4~5시간의 수동 과정을 자동화된 자율 검증 루프 속으로 격리한다.
- **Generator-Evaluator 이중화**: 코드를 실질적으로 작성하는 대형 생성 모델(Generator Model)과, 인수 조건 충족 여부를 고속 검사하는 경량 평가 모델(Evaluator Model)의 역할 분리를 통해 루프의 수렴 속도를 높인다.
- **안전 조건 필수화**: 조건이 모호할 경우 무한 루프에 빠져 대량의 API 요금을 청구하게 되므로, 종료 코드 0 등의 정량적 인수 조건(Acceptance Criteria)과 최대 루프 제한(Max Iterations) 장치가 요구된다.

## 상세
- **등장 배경**: AI 코딩 도구의 활용이 확대됨에 따라 Prompt Engineering(프롬프트 조작) $\rightarrow$ Context Engineering(컨텍스트 다듬기) $\rightarrow$ Harness Engineering(에이전트 제약 계층 설계)을 거쳐 최종적으로 에이전트 자율 루프 구조를 통합하는 Loop Engineering으로 진화하게 되었다.
- **루프의 형태**:
  - **반복 작업 (Recurring tasks)**: PR 상태 검사, 릴리스 로그 분석 등 주기적으로 반복 수행하는 루프.
  - **장시간 실행 작업 (Long-running tasks)**: 복잡한 리팩토링, API 마이그레이션 등 목표 달성 전까지 장시간 지속적으로 수행되는 골(Goal) 기반 루프.
- **골(Goal) 기반 자율화 요건**:
  - **Objective (목표)**: "특정 API의 레이턴시를 20ms 단축할 것"과 같은 구체적인 목표 상태 지표.
  - **Acceptance Criteria (인수 조건)**: 린트 및 단위 테스트 무사 통과(종료 코드 0) 등 정량적이며 결정적인 검증 요건.
  - **Constraints (제약 사항)**: 라이브러리 버전 제한 등 시스템이 절대 훼손해서는 안 되는 규정 범위.

## 예시
- **Claude Code의 `/goal` 명령 동작 흐름**:
  1. 개발자가 "api/newsFeed 지연을 20ms 이상 단축하라"는 `/goal` 명령 투입.
  2. 에이전트가 코드를 임시 수정(Generator Model 동작).
  3. 평가 엔진이 벤치마크 테스트 스크립트를 기동하여 지연 시간 단축량이 15ms임을 측정(Evaluator Model 동작).
  4. 인수 조건 불충족으로 판단하여 에이전트에게 2차 루프 명령 전달.
  5. 추가 수정 후 2차 검사에서 22ms 단축 확인(인수 조건 통과) $\rightarrow$ 루프 중단 및 결과 머지.

## 충돌
- **결정론적 쉘 스크립트 vs LLM 자율 루프**:
  - 빌드 체크, 단순 린팅 등 결과가 완전히 고정된 작업에 LLM 기반 자율 루프를 무작정 연동하게 되면, 토큰 비용이 낭비될 뿐만 아니라 통계적 불안정성으로 인해 헛손질을 반복하는 비효율이 발생한다. 따라서 결정론적인 정적 분석이 가능한 일은 쉘 스크립트와 Cron 구조로 묶어 처리하고, 실패 원인의 추론 및 다음 액션의 구조적 선택 등 지능적 판단이 요구되는 구간에만 Loop Engineering을 제한적으로 주입하는 경계 획정이 요구된다.
