# 풀 리퀘스트 위험도 산정

## 한 줄 정의
풀 리퀘스트(PR) 제출 직전, 수정한 소스 코드의 전역 호출 빈도, 테스트 커버리지, 보안 취약성 등 다각적 요소를 정적 분석을 통해 가중치로 합산하여 잠재적 장애 및 변경 영향 범위(Blast Radius)를 계량화하고 병합 여부를 제어(Gate)하는 정적 분석 기반의 개발 워크플로우이다.

## 핵심 요지
- **다각적 리스크 계량화**: 수정한 코드가 시스템 전체에 미치는 파급 효과를 단순 파일 단위가 아닌 호출 빈도, 테스트 케이스 유무, 특정 키워드 등을 조합하여 0~100점 혹은 특정 상한선 내의 점수로 수치화한다.
- **병합 게이팅(Gate) 자동화**: 산정된 위험 점수가 사전에 정의한 임계값을 초과할 경우, CI/CD 파이프라인에서 자동으로 PR 병합을 보류하고 추가적인 휴먼 리뷰를 강제하는 게이트웨이 역할을 수행한다.
- **리뷰 리소스의 선택과 집중**: 모든 PR에 동일한 에너지를 쏟는 대신, 위험 점수가 높게 산정된 핵심 변경 영역(예: 인증 결합부, 광범위한 공통 유틸 등)에 리뷰어의 주의를 집중시켜 검토 효율을 최적화한다.
- **예측 한계와 필터링 도구 활용**: 이 수치는 장애 데이터로 학습한 AI 예측 모델이 아니므로, 절대적 지표로 맹신하기보다는 위험한 패턴을 1차적으로 걸러내는 경고등(힌트)으로 간주해야 한다.

## 상세
풀 리퀘스트 위험도 산정 워크플로우는 소스 코드를 [[tree-sitter]] 등의 구문 분석기로 파싱하고, 그 결과를 바탕으로 함수/클래스 간 의존 관계 그래프를 빌드하여 리스크를 종합적으로 정량화한다 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`). 

1. **위험 점수(Risk Score) 산정 알고리즘 구조**:
   위험도는 정적 분석 도구(예: [[code-review-graph]])가 코드의 다각적인 요소를 파싱하여 가중치를 부여하고, 이를 합산하여 점수를 계산한다 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`). 6가지 주요 가중치 요인은 다음과 같다:
   - **전역 호출 빈도(Call Frequency)**: 수정한 함수가 시스템 전체에서 얼마나 널리 호출되는지 여부 (호출 노드가 많을수록 결함 발생 시 파급 범위가 비약적으로 증가하므로 가장 큰 가중치 부여).
   - **테스트 보장 유무(Test Coverage)**: 수정한 코드 영역을 검증하는 활성 단위 테스트 케이스의 존재 여부.
   - **보안 민감성(Security Sensitivity)**: 수정 범위 내에 `Auth`, `Credentials`, `SSL`, `Token` 등 보안 및 취약성과 직결되는 핵심 예약어가 포함되었는지 여부.
   - **순환 복잡도 및 코드 변경량**: 변경된 라인 수 및 수정이 가해진 함수의 복잡도 증가율.
   - **간접 의존도(Transitive Dependencies)**: 직접 호출되지는 않지만 체인 경로를 통해 간접적으로 연결된 다른 모듈의 수.
   - **기타 수정한 영역의 가중치 요인** 등 총 6가지 요소의 합산 및 상한선(Limit) 적용 구조.

2. **워크플로우 절차**:
   - **단계 1 (코드 수정 및 로컬 인덱스 갱신)**: 개발자 또는 [[코딩 에이전트]]가 로컬 환경에서 코드를 편집한 후, 수동 또는 CI 트리거를 통해 의존성 그래프를 업데이트한다.
   - **단계 2 (위험도 자동 조회 및 점수 산정)**: PR을 생성하기 전 `code-review-graph` 등을 실행하여 영향 범위(Blast Radius)를 쿼리하고 종합 위험 점수를 도출한다 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`).
   - **단계 3 (게이팅 판단)**: 점수가 사전에 정의된 위험 수준 상한선을 초과하면 빌드 파이프라인에서 경고를 발생시키며 즉각적인 머지를 보류한다.
   - **단계 4 (리뷰어 지정 및 심층 검토)**: 고위험 점수가 부여된 핵심 코드(예: 간접적인 전파 경로인 `proxy.ts` 등)에 대해 시니어 엔지니어가 코드의 맥락과 영향받는 구체적 테스트 케이스를 추적해 정밀 검증을 수행한다.

3. **실무적 유의사항 및 한계점**:
   - **자동 동기화 오작동 경계**: 로컬 분석 도구의 특성상 편집 도중 파일이 저장되면 이전 해시 기준으로 인덱싱되어 부정확한 점수가 나올 수 있으므로, 최종 위험도 조회 전 반드시 인덱스를 수동으로 재구축(`code-review-graph build`)해야 안전하다 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`).
   - **허위 탐지(False Positive) 비율 감안**: 정적 도구가 탐지한 파급 범위에 속한 노드 중 약 40%(10개 중 4개)는 실제 동작에 영향이 없는 거짓 매칭일 수 있으므로 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`), 산정된 수치를 의사결정의 1차 필터로 삼고 개발자가 교차 검증을 병행하는 것이 필수적이다.
   - **쿼리 범위(Blast Radius) 제한**: 넓은 파급 범위 조회를 무분별하게 실행하면 출력이 최대 596KB 이상으로 급증하고 노드 누락이 유발되므로, 평소에는 조회 범위를 좁히는 튜닝이 요구된다 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`).

## 예시
### 가중치 기반 위험도 계산 시나리오 (예시 모델 및 계산)
어떤 코딩 에이전트나 개발자가 OmniRoute 저장소의 핵심 인증 함수인 `classifyRoute`를 수정했다고 가정하자.

```python
# 풀 리퀘스트 위험도 가중치 점수 산정 개념 코드
def calculate_pr_risk_score(change_details):
    # 6개 요인 가중치 매핑
    weights = {
        "call_frequency": 0.35,      # 전역 호출 빈도 (가장 높음)
        "test_missing": 0.25,        # 테스트 누락 여부
        "security_keyword": 0.20,    # 보안 민감도
        "complexity_delta": 0.10,    # 복잡도 변화량
        "indirect_dependency": 0.05,  # 간접 의존 경로 수
        "lines_changed": 0.05        # 수정 코드 라인 수
    }
    
    score = 0.0
    
    # 1. 호출 빈도 계산 (예: 50회 이상 호출 시 최대점)
    calls = change_details.get("call_count", 0)
    score += min(calls / 50.0, 1.0) * weights["call_frequency"] * 100
    
    # 2. 테스트 부재 여부 (테스트 파일이 전혀 없으면 1.0)
    if change_details.get("test_cases_count", 0) == 0:
        score += 1.0 * weights["test_missing"] * 100
        
    # 3. 보안 키워드 매칭 여부 (Auth, Credentials, Token 등 포함 시 1.0)
    if change_details.get("has_security_keywords", False):
        score += 1.0 * weights["security_keyword"] * 100
        
    # 4. 순환 복잡도 증가량 (증가량이 5 이상일 때 최대점)
    complexity = change_details.get("complexity_increase", 0)
    score += min(complexity / 5.0, 1.0) * weights["complexity_delta"] * 100
    
    # 5. 간접 의존 경로 (체인 관계 파일 수)
    indirect_paths = change_details.get("indirect_paths_count", 0)
    score += min(indirect_paths / 10.0, 1.0) * weights["indirect_dependency"] * 100
    
    # 6. 수정된 코드 라인 수
    lines = change_details.get("lines_count", 0)
    score += min(lines / 200.0, 1.0) * weights["lines_changed"] * 100
    
    # 상한선(limit) 적용: 최대 100점
    return min(score, 100.0)

# classifyRoute 변경 사항 파싱 결과 대입 예시
classify_route_change = {
    "call_count": 42,                  # 호출 빈도 높음
    "test_cases_count": 4,             # 구체적 테스트 4개 존재 (점수 가점 없음)
    "has_security_keywords": True,     # Auth/Route 키워드 검출됨
    "complexity_increase": 2,          # 소폭 복잡도 증가
    "indirect_paths_count": 3,         # runAuthzPipeline 거쳐 proxy.ts 등으로 연동
    "lines_count": 15                  # 적은 양의 수정
}

risk_score = calculate_pr_risk_score(classify_route_change)
print(f"classifyRoute의 위험 점수: {risk_score:.2f} / 100.0")
# 결과 출력: 64.90 / 100.0 (CI에서 경고 기준 60점을 넘었으므로 자동으로 병합 게이팅 발생)
```

## 충돌
- **정적 분석 vs 런타임 추적의 정확도 충돌**: 정적 분석 도구인 `code-review-graph`는 tree-sitter 파싱을 통해 의존 관계를 보증하나, 40%의 허위 탐지(False Positive)를 수반한다 (`raw/Andrej Karpathy’s Fix for LLM Memory Works on Code Too.md`). 반면 런타임 분석이나 동적 추적 방식은 정확도가 높은 대신 테스트가 실행되어야만 파급 효과를 식별할 수 있다. 이에 따라 "빌드 전 정적 분석으로 1차 고위험군을 게이팅하고, 실제 병합 시에는 동적 테스트 커버리지를 보장하는 하이브리드 검증 방식"이 절충안으로 권장된다.

## 관련 노트
- [[code-review-graph]]: PR 위험도 평가 기능을 내장하고 가중치 기반 분석을 로컬에서 수행하는 핵심 도구.
- [[codegraph]]: 의존성 파급 범위(Impact)를 빠르게 탐색하는 데 특화된 범용 정적 분석 도구.
- [[코드 변경 영향 범위 분석]]: 코드 수정에 따라 직접/간접적으로 영향받는 범위를 탐색하고 파생 영향을 계량화하는 연관 기법.
- [[코드 리뷰 대기열 병목]]: PR 위험도 산정을 통해 병목이 발생하는 대기열에서 고위험 PR과 저위험 PR을 차등 처리함으로써 프로세스를 최적화하는 관계.
- [[코딩 에이전트]]: 정적 그래프 지식을 바탕으로 인지적 비용을 최소화하며 PR 전 위험도를 스스로 점검하는 주체.
